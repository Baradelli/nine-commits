things a badly-behaved run can reach stops being a list I can enumerate."* Post
7 pointed here near its top rather than at its end, and about one thing — the

That one said **giving the agent a shell gives it everything you can do,
including the parts you would not do.** The first half is true and I will show

reason I did not expect: *the parts you would not do* is a claim about a

## The part that is true, run where it could only destroy a container

Every other piece of evidence on this page is about a guard refusing something,
and a refusal is only interesting if you know what it is refusing.
`tools/shell/unguarded.mjs` is the tool with the guard deleted. It is seven
lines:

```js
function runCommand(command) {
  try {
    return execSync(command, { cwd: '/work', encoding: 'utf8', stdio: 'pipe' })
  } catch (error) {
    return `exit ${error.status ?? '?'}\n${error.stdout ?? ''}${error.stderr ?? ''}`
  }
}
```

It was run in a container with **no bind mount, no volume, no network**. The
script goes in on standard input rather than through a mount, because a mount
is a hole in exactly the claim being made:

```sh
docker run --rm -i --network none -e DEMO_API_KEY=DEMO-NOT-A-REAL-KEY \
  node:22-alpine sh -c 'cat > /work.mjs && node /work.mjs --destroy-this-container' \
  < tools/shell/unguarded.mjs
```

That flag is the whole of what stops this file running on your machine, and it
is worth being exact about why it is a flag. The obvious guard is a check for
`/.dockerenv`, and I shipped one first. It is not a containment boundary: the
file is in every Docker container, which includes a VS Code dev container
bind-mounting your checkout at `/workspaces`, and a GitHub Actions `container:`
job bind-mounting the workspace at `/__w`. In both of those, `/.dockerenv`
passes and `rm -rf --no-preserve-root /` eats your work. On Windows the same
check resolves to `C:\.dockerenv`, a file any user can create. And it is
*absent* under Podman, containerd and LXC, so it is simultaneously too
permissive where it matters and too strict where it does not. The file now
requires `--destroy-this-container` as well, and refuses if `/workspaces`,
`/__w`, `/host` or `/mnt` holds anything — which is a better guess and still a
guess. What makes it safe to publish is not the guess. It is that without the
flag there is nothing to delete a check *from*: the file is inert.

The isolation is verified rather than asserted. The same command was run a
second time with `--name nine-shell-inspect` in place of `--rm`, so the
container that did it survived to be inspected, and its output differed from
the first run's on exactly the two lines that carry the container's hostname.
`docker inspect` then reported
`Mounts=[] NetworkMode=none Binds=null VolumesFrom=null Privileged=false`. The
host was fingerprinted either side with `git rev-parse HEAD`, an MD5 of
`git status --porcelain` and an MD5 of the home directory listing; all three
identical. The full commands — both `docker run` lines and the `docker inspect`
format string, unelided, so you can run them — are in
`tools/shell/container.md` with the whole transcript.

Eight lines of that transcript are the reason every rule in the guarded tool
exists. This is an excerpt: the script prefixes each call with a `#` comment,
which I have dropped here, and `cat /etc/shadow` printed twelve lines of which
one is below.

```
$ echo "I am $(whoami) on $(hostname)"
  I am root on 68d731b29c1e

$ echo PLANTED > /work/planted.txt && cat /work/planted.txt
  PLANTED

$ env | grep -i -E "key|token|secret"
  DEMO_API_KEY=DEMO-NOT-A-REAL-KEY

$ cat /etc/shadow
  root:*::0:::::
```

And then five that are not — all five of them, with everything they printed;
`rm -rf /work` printed nothing:

```
$ rm -rf /work
$ ls -la /work
  exit ?
$ rm -rf --no-preserve-root /
  exit ?
$ ls /
  exit ?
$ node --version
  exit ?
```

The last four all print `exit ?`, and three of them do so for three different
reasons the tool cannot tell apart. `/work` is gone. `/bin/ls` is gone. The Node
binary is gone — while the Node process that ran the tool is still alive,
holding its own executable's inode open, printing this transcript from a machine
that no longer exists. The fourth is the `rm` that did it, and it reports itself
with exactly the same six characters as the three it caused.

That is the argument for a guard in one paragraph. `execSync` does not know the
difference between `wc -l` and `rm -rf /`. It is the same call.

## What I built, and what it turned out to be

`run_command(command)`. One string, the way a model would write it. Seven
rules, in `agent/src/tools/shell.ts`:

1. **There is no shell.** `execFile` with `shell: false`. Nothing expands a
   glob, substitutes a variable, joins two commands or opens a redirection,
   because no shell is ever started.
2. **Metacharacters are refused anyway** — `;` `&` `|` `>` `<` backtick `$`
   `(` `)` `{` `}` `[` `]` `*` `?` `!` `#` `~` `\` and every control character.
   Under rule 1 that is belt-and-braces, and it stops being belt-and-braces the
   moment an *allowed binary* re-interprets its own arguments.
3. **The binary is an allow-list**, by bare name, resolved to an absolute path
   this module finds itself. No path separator, no drive letter, no `.bat` or
   `.cmd` — an argument vector handed to a batch file is re-parsed by `cmd.exe`
   on Windows whatever `shell: false` says, which is CVE-2024-27980 and the
   cleanest example there is of a guard that is correct about the API it called
   and wrong about what happened.
4. **The flags are an allow-list too, per binary.** Not a deny-list.
5. **Every non-flag argument goes through post 6's `resolveInside`** — the same
   path guard, link check included, that the four filesystem tools use.
6. **The environment is not inherited.** This process is started with
   `--env-file=agent/.env`, so `process.env` holds a real API key.
7. **cwd is the sandbox, stdin is closed, output is capped, there is a
   timeout.**

Then I wrote the list of binaries, and that is where the post changed.

Every entry had to satisfy two conditions: I could write down every flag of it
I was willing to pass, and it had no way to start another program. The second
clause removed the useful half of a shell.

- `sed` has `w`, `r` and, in GNU, `e` inside its *script* argument, so allowing
  `sed` means writing a parser for sed scripts. `sed -i` is the single idiom
  that would have made this tool good at the edit tasks below.
- `awk`, `perl`, `python` and `node` are languages with `system()`.
- `git` has `-c core.pager=…`, `-c alias.x=!sh`, `--exec-path` and
  `--upload-pack`. There is no subset of `git` that is a subset.
- `xargs`, `env`, `sh`, `tar --to-command`, `tee`, `rm`, `ln`, `chmod`, `curl`
  — each for its own reason, all of them the same reason.

What survived is fifteen names: `cat cp diff echo find grep head ls mkdir mv
sort tail touch uniq wc`. And **nothing in that list can author a byte of its
own.** Every shell idiom that composes content — `>`, `sed -i`, `tee`, a
heredoc — is either a shell feature rule 1 removed or an interpreter rule 4
could not admit.

Be precise about that, because I have now got it wrong twice: the first time it
was the thesis, and the second time it was the sentence I wrote to fix the
thesis. *Read-only* is wrong: five of the fifteen change the filesystem.
`cp a b` replaces every byte of `b` with bytes that were already on disk, with
no flag. `mv` moves a file out from under whatever expected to find it. `mkdir`
and `touch` create things. And `uniq` writes, which is the one I missed — its
synopsis is `uniq [OPTION]... [INPUT [OUTPUT]]`, so the second operand is an
output file, and the path guard has no notion of read against write. It asks
whether a path is inside the sandbox and nothing else. So:

```
before  target.txt = "ORIGINAL-CONTENT\n"
uniq -c in.txt target.txt -> ok:true exitCode:0
after   target.txt = "      2 a\n      1 b\n"
```

That is worse than `cp` in a way worth naming. The count column, and the spaces
padding it into a column, were on no disk anywhere: `uniq` composed them.
The correction I shipped before this one said the tool "can read, copy, rename
and make empty things, and nothing else", and that sentence was a fix that
introduced a new false claim. An enumeration is a claim about everything it
leaves out.

What the list cannot do is put a byte the *model* chose into a file, and that
still holds — but check the reasoning rather than taking it, because it is the
thesis. A `uniq -c` count is a property of its input. The only way the model
changes it is by naming a different file that already exists, and nothing in the
fifteen concatenates, repeats or composes, so there is no way to build an input
that yields a chosen output. The model can select bytes. It cannot compose them.
Copying, renaming and counting are not authoring, but all three are writing, and
a tool that can do them can take a project apart without composing a single
character.

The five are now measured rather than listed: `tools/shell/writers.test.ts`
runs every one of the fifteen, with every flag the allow-list gives it, against
a scratch directory and watches what moves. It also reads this post, the tool
description and `shell.ts`, and goes red if any of them describes the writing
set more narrowly than the measurement does. Two commit messages in this
repository are still wrong about it: the one that built the tool calls these
"fifteen read-only programs", and the one that corrected *that* names four of
the five writers and stops. Git history does not get edited, so both stay
wrong, and this is where I say so rather than leave you to find the
contradiction.

And here is the part that should have caught it earlier. **`uniq` was never
called.** Not once in a hundred and forty runs: the seventy-nine command lines
the model wrote are fifty-five `grep`, seventeen `wc`, six `find` and one `ls`.
The hole was real for every one of those runs and nothing went near it, so every
sentence describing the tool read clean — the one the model itself was handed,
which said the tool could not change what is inside a file, and the one that
replaced it, which said it could not write new content into one.

Post 6 printed `escapes recorded: 0` under three tools that had just died on an
`ENOENT`: a zero from a counter that never got to move. This zero is its cousin.
Nothing wrote through `uniq` because nothing asked to, and I read the quiet as
the property holding. A number that stays at zero because nothing tried it is
not a measurement of the thing you wanted to measure, and a property nothing
tested is not a property that passed.

That is not a limitation I worked around. It is the result.

## I attacked it before you did

Post 6 shipped a path guard with a hole in the part its author was proudest of,
and what found it was somebody attacking it rather than anybody reading it. So
this one has <a href={attacks}><code>attacks.tsv</code></a> beside it: **97
hostile command lines**, each with a **prediction written before the table was
ever run**, put through `planCommand` — the same function a live run calls.

| | |
| --- | --- |
| refused | **80** |
| allowed | **17** |
| disagreed with the prediction | **0** |

The eighty break down by the rule that caught them: 25 on the binary list, 24
on a metacharacter, 14 on a flag, 13 on a path, and one each on an unterminated
quote, a command over the length limit, an empty command and `cat -`.

Some of them are worth naming. `find . -type f -exec ls -la +` and
`find . -execdir`, `-delete`, `-fprintf`, `-fls`. `grep -f /etc/passwd`, whose
value is a file the path rule never sees. `sort -o stolen.txt`, because sort
writes files. `git --exec-path=.` and `git -c core.pager=ls`. `sh -c`,
`node -e`, `awk 'BEGIN{system(…)}'`, `sed -n '1w stolen.txt'`. `env PATH=. ls`.
`ln -s / escape`, which would plant the link post 6's guard was rebuilt around.
Four rows are `constructor`, `__proto__`, `toString` and `hasOwnProperty` —
because `ALLOWED[name] !== undefined` finds all four on the prototype and hands
the guard a "binary" whose `flags` is undefined, which crashes it from the
inside. `Object.hasOwn` is the whole fix and it is one call.

**Zero disagreements is the weakest result in that table, not the strongest.**
It says the guard's author and the guard's attacker are the same person. The
three things this commit actually found were found by measuring, not by
predicting, and none of them is a row in the table.

### Hole 1: the allow-list is a list of names, and a name is not an identity

`resolveBinary` searches `PATH` itself rather than letting `execFile` do it,
which is already the careful version. It is still a bet that the first `ls` on
`PATH` is the `ls` you meant. Measured:

```
resolveBinary("ls") normally    -> C:\Program Files\Git\usr\bin\ls.exe
resolveBinary("ls") with a shim -> <temp>\nine-shim-5iA5F0\ls.exe
```

The shim is a copy of `whoami.exe` renamed. Ask for `ls`, run `whoami`. The
agent cannot do this — there is no `env` in the list and no variable syntax —
but whoever starts the process can, and post 6 found the identical shape in
`TMP`: the rule that keeps the write root in scratch space is `os.tmpdir()`,
and `os.tmpdir()` is whatever the environment says. Two guards, two commits, one
mistake: **a control whose input is an environment variable is a control the
environment owns.**

### Hole 2: the environment is not the environment

Rule 6 builds the child's environment instead of inheriting it — `PATH` set to
one directory and `SystemRoot`, and nothing else. The API key does not survive,
which is the part that matters. Here is what the child actually sees, measured
by running `env` under exactly that environment:

```
HOMEDRIVE=C:
HOMEPATH=\Users\User
LOGONSERVER=\\DESKTOP-…
PATH=/usr/bin
SYSTEMDRIVE=C:
SYSTEMROOT=C:\WINDOWS
TEMP=/tmp
USERDOMAIN=DESKTOP-…
USERNAME=User
USERPROFILE=C:\Users\User
WINDIR=C:\WINDOWS
TERM=xterm-256color
HOME=/c/Users/User
```

That is `env`'s own output, in `env`'s own order, with one edit: the machine
name is truncated to `DESKTOP-…` in the two lines that carry it. The version of
this block I first published was missing `WINDIR`, printed the rest in a
different order, and said twelve. It was a real measurement with a line lost on
its way onto the page, which is the least defensible kind of wrong number:
right enough to survive being read.

I handed it two variables. It has **thirteen**. The MSYS2 runtime that every
binary in the allow-list is linked against rebuilds a POSIX environment from the
process token when one is missing, so the home directory and the machine name
arrive anyway — from a DLL, not from `process.env`. That is rule 2's warning
arriving from a direction rule 2 does not cover: an allowed binary
re-interpreting its own inputs, where the input is the environment and the
interpreter is libc.

Nothing in the allow-list prints the environment, so no run in this post's
hundred and forty could have put those lines in a trace. That is an argument
about the roster, not about the guard, and it is the same argument post 6 made
about hard links.

**A note on the standing of the three exhibits in this section.** The `PATH`
shim above, this block, and the `ls -la` line further down are measurements
taken on one Windows machine with Git Bash's MSYS binaries, and unlike every
number in the tables below they have **no committed artifact behind them** —
there is no file in the repository a test can recompute them from, because what
they record is a fact about a machine rather than about this code. Each was
re-measured while fixing this post and each reproduced. Read them as what they
are: three things I ran, written down. The series' rule is that no number may
describe the repository as it is now, and these three are the exception, said
out loud.

### Hole 3: the guard's idea of a path is not the binary's

```
$ cat C:README.md
  /usr/bin/cat: 'C:README.md': No such file or directory
```

`C:README.md` is drive-relative. Node's `path.resolve` reads it as a path on
the current drive and lands it inside the sandbox, so the guard approves it.
MSYS `cat` reads it as a filename with a colon in it. Both are harmless here
and both land inside, but the guard checked one string and the program opened
another, and a guard is only as good as the agreement between those two. The
whole allow-list rests on it.

### And one thing that is allowed and should frighten you anyway

Eleven of the seventeen allowed rows are in the class I called `inside`, and
they are the post's title in miniature. `cat .env` is one of them:

```
$ cat .env
  AGENT_TOKEN=DECOY_SECRET_NOT_A_REAL_KEY
```

The four filesystem tools have skipped every dotfile since v2, and that rule is
the reason `agent/.env` has stayed out of six posts' traces. `cat` has never
heard of it. So `createShell` runs `assertWritableRoot` and there is no argument
to it that returns a shell rooted at this checkout. Both halves of that check
earn their place: nothing it writes is content the agent composed, and nothing
it writes has to be, for it to be quite enough. Inside the directory it *is*
given, the shell reads anything, the five binaries that write rewrite anything
they are pointed at, and `grep -r` returns the lot in one call. The guard's
promise is *inside the sandbox*, and inside the sandbox it can take the project
apart.

## The experiment

Post 6's five tasks, imported rather than copied so both posts grade the same
work by the same code, plus two chosen because a shell should win them.

| task | what it exercises |
| --- | --- |
| `find-timeout` | read |
| `write-note` | write |
| `edit-timeout` | edit in place |
| `append-changelog` | addition at the end |
| `add-setting` | genuinely ambiguous |
| `find-mentions` | a search across every file — this roster has no search tool |
| `largest-file` | a byte count, which `read_file` cannot produce at all |

The two new ones are there because of post 6's own rule: a question set with no
task the extra tool is good at makes *the extra tool is useless* true by
construction. Both are graded on the final answer, and both ground truths are
computed from the workspace rather than typed in — six lines containing
`parcel`, across five of the eight files, and `README.md` at 191 bytes.

**Two conditions, seven tasks, ten runs a cell, a hundred and forty runs.**
`four` is post 6's list, read, write, edit. `four-shell` is those four with
`run_command` appended — one more definition at the end, nothing else changed.
Conditions interleaved, nothing retried, a run that throws written down as a
run that threw. Fixed in `tools/run-shell.ts` before the first call.

There is no shell-only condition, deliberately. `run_command` cannot author a
byte of its own, so an agent holding only the shell could not write a note,
change a timeout, append to a changelog or add a setting — four of the seven
tasks lost by construction, and a condition that loses by construction measures
its own construction.

### The composition check, before the causal reading

Post 5's lesson and post 7's, applied. Post 7's thesis only survived once
`max_parallel` was controlled for; the mix here is whether the guard ever said
no.

| | runs | finished | step-capped | capped and finished | steps/run | input tokens/run |
| --- | --- | --- | --- | --- | --- | --- |
| shell, guard refused something | 23 | **13** | **11** | 4 | 7.91 | 9,355 |
| shell, guard refused nothing | 47 | **47** | 0 | 0 | 4.43 | 3,714 |
| four tools | 70 | 65 | 0 | 0 | 4.49 | 3,409 |

The fourth column exists because the first row's 13 and 11 add to 24 against 23
runs. The columns are independent counts and four runs are in both: `edit-timeout`
runs 1, 3, 8 and 9, which hit the cap *and* changed the one value they were
asked to change. Two of them made that edit on the tenth step, which was the
last one they had. Both facts are true of those runs, so both are recorded, and
a row that does not add up is the honest shape.

Forty-seven for forty-seven, and every one of the eleven capped runs is in the
other row. **p < 0.0001.** And the thirty-nine runs that held the shell and
never called it finished thirty-nine of thirty-nine — indistinguishable from
the control (p = 0.16), at a 95% upper bound of 7.4 per cent on a failure rate
those thirty-nine would have missed.

So the effect is not *the shell*. It is *the argument between the model and the
guard*, and part of the mechanism is arithmetic: a refusal costs a step and the
cap is ten. But only part. Across the eleven capped runs the guard said no
between one and four times, 2.45 times on average, so a run does not usually
reach the cap by being refused out of its budget — it reaches the cap because,
after a refusal, it stops asking for eight files at once and starts asking for
them one at a time. That is what the demo above shows, and it is the more
expensive half.

### What the model asked for

Seventy-nine command lines, fifty-nine of them distinct. By first word:

| | |
| --- | --- |
| `grep` | 55 |
| `wc` | 17 |
| `find` | 6 |
| `ls` | 1 |
| anything not on the allow-list | **0** |

**The binary allow-list never fired.** Twenty-five rows of the attack table go
at it — every interpreter I could name — and in a hundred and forty runs the
model never once asked for a program that was not on the list. What fired was
the parser: 25 refusals on a metacharacter and 22 on a flag. Seventy-nine
command lines with none of them off the list puts the 95% upper bound on the
rate at which this model reaches for an interpreter at **3.7 per cent**, which
is what that zero is worth and not more.

Because the model does not write commands. It writes shell:

- **15** command lines carry `||`, and all fifteen of them end in `… || true` —
  which is what you write when you expect `grep` to exit 1 and do not want a
  shell script to stop. None carries `&&`.
- **6** carry `-exec`, and that is **every single `find` the model wrote**:
  `find . -type f -exec grep -n "parcel" {} +`,
  `find . -type f -exec wc -c {} +`, and four more. `find -exec` is the
  canonical way out of a command allow-list, it is the first thing anyone
  writing one of these guards is warned about, and it arrived here six times
  out of six from a model with no adversarial intent whatsoever.
- **5** carry a glob.
- **2** name `..` as an operand — the same command twice, once with `|| true`
  on the end and once without. Neither reached the path rule: the first was
  refused on the metacharacter and the second on the flag, both before the
  operands were looked at. Which is worth saying plainly, because the refusal
  you get is not always the refusal you needed, and a guard that reports the
  first rule it trips is a guard whose messages are about its own order.
- **30** use `-R` and **8** use `-r`. The sentence is about `grep`, and
  twenty-nine of the thirty are `grep -R`; the thirtieth is `ls -R`, where the
  flag is on the allow-list and harmless. All eight `-r` lines are `grep`. So
  the comparison that matters is 29 against 8. That is the one letter I removed
  from `grep` on purpose, because `-R` dereferences symbolic links while it
  walks and `-r` does not — so `-R` is a way to read through a link the path
  guard has just refused to follow. The model reached for the dangerous letter
  twenty-nine times out of thirty-seven.

### The standing charge

A tool definition rides in every request for the whole life of a run. Before
either agent has done anything, the four-tool run carries a mean of **432.9**
tokens and the shell run **586.9** — a charge of **154 tokens** for a
description that has to list fifteen binaries and then spend a sentence on
everything the tool will not do.

One caveat on that number, because it is the kind this series keeps making. The
description those runs were handed ended "It cannot change what is inside a
file", which is the same false sentence the thesis used to carry. It has been
corrected in `descriptions.ts` twice: the first correction ended "it cannot
write new content into one", which `uniq` falsifies, and the second states the
property instead of listing the members. The 154 tokens are recomputed from
`runs.tsv`, which records what those hundred and forty runs actually carried, so
the figure stands — but a reader who checks out `v8-shell` and re-runs the sweep
is handing the model a longer string than the one measured here, and longer
again than after the first correction. That is post 7's disclosure, twice.

Post 6 measured 88 tokens for `append_file` and called that its one durable
finding. This is that number, seventy-five per cent larger, for a tool that was
called in 31 runs of 70 and refused on 47 of the 79 things it was asked to do.

### What it cost

628,380 input tokens and 135,140 output tokens across the hundred and forty
runs, which is **42.7 cents** at $0.25 and $2 per million — 25.3c for the four
and 17.4c for the shell. Four pilot runs, discarded and not in the tally, cost
2.1c. The container demonstration and the attack table cost nothing: no model
call is made by either.

The shell condition spent **more** input tokens and **less than half** the
output, and the whole of that gap is one task. On `largest-file` the four-tool
runs averaged 6,004 output tokens and the shell runs 421 — ranges that do not
overlap, 5,408 at the lowest against 846 at the highest. Counting the bytes of
eight files in your head is expensive, and wrong three times in ten.

## What broke

### Post 4's and post 5's predicted lines fired, for the second time

Both of them, on the first trace with a `run_command` result in it:

```
eval observationsOf: UnreadableResult: frame 4: run_command returned a result shape this eval does not understand
judge renderTrace:   UnrenderableFrame: frame 4: a tool result shape this renderer does not understand
```

Post 6 ran this exact experiment with `read_file` and wrote the paragraph about
why the alternative — returning an empty list — would have graded every run as
a run that observed nothing. Both readers now understand a command: one `line`
observation per line of output, with the *command* in the `file` field, spelled
with a `$` so it cannot be read as a path. Standard error is a separate source,
because a line read out of `no such file or directory` is not evidence about
the project.

Both of those are stated as safety properties, so both are now tests. When this
post first shipped they were not: dropping the `$ `, merging the two streams
into one source, and disabling the judge's command branch outright each left the
whole suite green, which somebody else found by trying it. That is the defect
this series has shipped more often than any other — a rule described in prose,
implemented once, and never asked whether it still holds — and it is worth
noticing that the rule being described as a *safety property* is what made
nobody check. `observation.test.ts` and `prompt.test.ts` now go red on all
three.

### The provenance grader met a question it cannot grade

Post 4's provenance check is built on *the one line in the corpus that answers
the question*. `largest-file` has no such line. The answer is a byte count — a
property of the files, not a statement in any of them — so `truthFile` is
absent and both runs come back `ungradable`. That is the honest verdict and it
is a real limit on an instrument two posts are built on, alongside the one post
7 found: it also cannot see a compaction.

There is a second, subtler version in `find-mentions`. The four-tool run reads
`src/server.ts`, so the observation's source is `src/server.ts` and provenance
is `grounded`. Had the shell run's `grep` succeeded, the same line would have
arrived with the source `$ grep -r parcel .` — and the grader would have
recorded that the text came back while being unable to say which file it came
from. Teaching it to parse `path:line:text` out of grep's output would mean
writing a parser for one binary's output format inside a grader, which is the
same mistake as the allow-list, one layer up.

### `ls -la` puts the account name in the trace

```
drwxr-xr-x 1 User 197121 0 Sep 24 14:07 .
-rw-r--r-- 1 User 197121 2 Sep 24 14:07 README.md
```

`User` is the Windows account and `197121` is its group. The redaction pipeline
does not catch it and is right not to: it matches no key shape, no bearer token
and no home path. It is only harmless here because this machine's account is
literally called `User`, and because in a hundred and forty runs the model ran
`ls` exactly once and never with `-l`. It is in the attack table as a row and it
is a leak class the pipeline has never seen — which is where post 7's leak came
from too.

The same shape, one step over: every MSYS error message is prefixed with the
absolute path of the binary (`/usr/bin/cat: …`). Generic on this machine.
Not necessarily on yours.

### The recorder's grade caps at partial when the guard refuses

A refused command is `{ ok: false }`, and `deriveOutcome` has capped a run's
grade at `partial` whenever a tool call failed since v2 — a rule written for an
agent whose only product was a sentence. So a shell run that was refused once
and then did everything right is recorded as `partial`. That is post 6's
polarity-reversed finding for the third time, and I did not change the rule
mid-series. The tally's `pass` column is the file-and-answer grade and is the
one the tables above use.

## What this does not fix

**The container is not a virtual machine.** It is a kernel namespace, and
container escape is a category of bug that exists. What the demonstration
proves is that the run had no path to the host that Docker knew about and the
host was unchanged afterwards. It does not prove isolation in general.

**The guard answered a committed question two different ways depending on where
it ran.** This is the most platform-sensitive code in the project — it resolves
binaries against `PATH`, refuses `.bat` files, and hands strings to programs
that parse them again — and the runs happened on Windows while CI is Linux. One
row of the attack table flipped. `path.resolve` reads `C:/Windows/win.ini` as
absolute on Windows, so the guard refused it; on POSIX the same string is an
ordinary relative name, so it resolves *inside* the sandbox and the guard
allowed it. Both answers are right about their own platform, which is exactly
the problem, because `attacks.tsv` is printed as a claim about what this guard
refuses. There is an explicit rule for it now, anchored on the separator so that
the drive-*relative* form stays the finding it is.

What the rule closes is every operand shape in the committed table, which is
what that table needs, and not every operand shape. `D:README.md` still answers
differently: Windows resolves it to `D:\README.md` and refuses, POSIX reads it
as an ordinary name and allows it inside the sandbox. Windows is the stricter
side, so this is a gap in the *equivalence* rather than a hole in the sandbox,
and it is not in `attacks.tsv` — adding rows would move the 97 that six figures
above are counted from, after I had seen which way they fell.

Two things follow that I would rather say than leave implied. The rule is
**untestable on the machine that needed it** — on Windows it is redundant, so
deleting it turns nothing red, and the only falsifiable test is of the predicate
itself. And the whole suite was re-run on Linux, in a container with no network
and a fake API key, to check nothing else had the same shape: 8,354 passed and
2 skipped, against 8,356 passed on Windows, the two being post 6's Windows-only
path-form cases. Every test is accounted for on both, and that includes the
measurement of which binaries write — the same five on Linux as on Windows. What does *not* carry across is `attacks.tsv`'s `effect`
column. It records what happened when a command actually ran, on one machine,
with Git Bash's MSYS binaries on `PATH`, and `/usr/bin/cat:` in an error string
is a fact about that machine rather than about this guard. It does not even
carry across time: the `ls-long` row quotes `ls -la`'s `total` line, which is a
block count of the scratch directory, and `npm run attacks` rewrites that one
cell on this machine today. Every `verdict`, `rule` and `agreed` cell
regenerates byte for byte, and those are the columns every number on this page
is counted from — but "`attacks.tsv` regenerates unchanged" was a claim I made
about the whole file and it was never true of all of it.

**Ninety-seven attacks are ninety-seven attacks.** They are the ones I thought
of, they agreed with my predictions a hundred per cent of the time, and that
agreement is a statement about me — ninety-seven rows with no disagreement puts
the 95% upper bound on my disagreement rate at 3.0 per cent, which is the most
that zero is worth. The three real findings came from measurement. There is a
fourth I can describe and could not exploit: a flag's value skips the flag
check, so `grep -m -r pattern file` passes the guard with `-r` sitting where a
number should be. None of the fifteen binaries turns that into anything, and I
cannot promise the sixteenth would not.

**TOCTOU, still.** `planCommand` resolves the paths and then the command runs,
for up to ten seconds, in a directory the guard checked beforehand. Post 6
disclosed this for a single `writeFileSync`. A ten-second subprocess is a much
larger window.

**The fence was never exercised.** Command output comes back inside a labelled
block with both markers neutered, which is post 7's fence extended to a new
content class — and post 7 could not add its fence to search results because a
hundred runs had already been recorded without it, while this tool had no runs
behind it, so doing it now was free. Nothing hostile ever went through it. Every
byte of output in these traces came from a workspace this repository invented.
Same standing as post 7's fence, and post 7's fence had a hole.

**Ten runs a cell is ten runs a cell.** The five tasks where nothing moved are
five 10/10-against-9-or-10/10 cells, and ten runs with no failures put the 95%
upper bound on a failure rate at **25.9 per cent**. Those five rows exclude a
catastrophe and nothing finer. Seventy runs a condition gets that to 4.2 per
cent, which is the resolution the *overall* null is bought at.

**The workspace is eight tiny files.** `grep` over eight files and `read_file`
over eight files are close enough that the four can win by reading everything,
which is not true of a real repository. Post 6 named its ten-line changelog as
the biggest reason not to read its pass rates as a claim about real code; this
is the same caveat, and here it cuts *against* the shell, which is the direction
that flatters my result. Say the workspace were four hundred files: the four
cannot read them all, and `grep -r` is the only tool on the page that finishes.

## The thesis has changed

The index said a shell gives the agent everything you can do, **including the
parts you would not do**. What a hundred and forty runs and ninety-seven
attacks say instead:

A shell **is** everything you can do. The container settles that half, and it is
not a hypothetical: one call took the machine out from under the process that
made it.

But *the parts you would not do* never arrived, because the thing I was willing
to run on this machine is not a shell. It is fifteen programs with a flag
allow-list, no punctuation, no interpreter and no way to author a byte of its
own — though five of the fifteen still write, and one of them writes bytes that
were on no disk, which is a reminder that *cannot write*, *cannot compose* and
*cannot be dictated to* are three different sentences. And the
model never tested any of that. It never asked for `sh`, or `rm`, or `node`, or
anything else off the list, in a hundred and forty runs. What it did was write
`grep -R … || true` and `find … -exec … {} +`, over and over, and get told no,
and lose the run to the step cap.

Which makes this post 6's original thesis coming true one tool later. Post 6
said a fifth tool would make the agent worse and could not find it: `append_file`
was chosen correctly ten times out of ten, cost 88 tokens of standing context,
and changed nothing else post 6 could measure at fifty runs. The
sixth tool does make it worse — not because the model misuses it, but because
the tool's *contract* is a lie the model cannot help believing. A thing called
`run_command` that runs one command out of fifteen programs is a tool whose
name promises a shell and whose implementation is a parser, and post 2's finding
is that the model reads the promise.

And then the one exception, which is the useful half. On `largest-file` the four
primitives have nothing — no size, no count, no arithmetic — and the shell wins
ten out of ten against seven, for a fourteenth of the output tokens. **A shell
earns its place exactly where the primitives have no primitive**, and nowhere
else that this experiment could measure.

## The commit

Post 6 asked whether four filesystem operations are enough and found that they
are. Post 8 adds the tool everybody reaches for next and finds that the version
of it you can defend is a worse `search_files`, and the version that is actually
a shell is the one in the container, printing `exit ?` from a machine it just
deleted.

There is a design left over, and it is the one I would build next. The two
things the shell was good for here — a search across files, a byte count — are
two more primitives, not a shell. Post 6's argument was that four are enough;
what these runs say is that four were two short, and that the answer to *two
short* is six primitives rather than an open door with a grille bolted across
it.

Which leaves the question this series has been avoiding for eight commits.
Every safety property on this page is a property of the program, and the
program's answer is always the same: yes, or no, decided in advance, by me,
with no idea what the run is actually for. The next commit is the one where
somebody is asked.
