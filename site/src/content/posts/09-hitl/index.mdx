## The frame that has been in the schema since commit 1

`tools/trace/schema.ts` has defined this since the first commit of the project,
before the agent could call a tool at all:

```ts
z.object({
  type: z.literal('approval'),
  tool: z.string(),
  decision: z.enum(['allow', 'deny']),
})
```

`Frame.tsx` renders it in three places — it has a colour, a label (`Allows` /
`Denies`) and a sentence for its body. A comment in `agent/src/run.ts` said
*"approval is post 9, and when it lands this function stops being a two-way
answer."*

And no trace in this repository had ever contained one. You can check that
against the tag this post is bound to:

```
git grep -l '"approval"' v8-shell -- site/src/content/posts/
```

It exits 1 and prints nothing. Eight posts, sixteen published traces, and a
frame type carried along in every one of them without a single instance.

Post 7 found `compaction` in exactly this state and made it real, and the moment
real data reached the rendering path it broke four things. This was the last
unexercised path in the schema, and it broke four more. They are in *What
broke*, and one of them had shipped a published trace saying a run had
succeeded when it had been stopped.

## What I built

An approval gate: before a tool that changes something runs, the run stops and
asks.

`agent/src/approval.ts` is the whole of it. A set of tool names, a function
that answers, and a sentence the model is handed when the answer is no.

```ts
export const GATED: readonly ToolName[] = [
  'write_file',
  'edit_file',
  'append_file',
  'run_command',
]
```

The rule is *does this change something that outlives the run*, which picks out
the three filesystem writes and post 8's command runner, and nothing else.
Reading a file, listing a directory, searching, and both of post 7's web tools
are outside it. A read that goes wrong wastes tokens; a write that goes wrong is
a file that is now different.

### The gate is a list of names, and that is the defect

The AI SDK's approval protocol hands the gate two things: the name of the tool
and the arguments the model wrote. That is everything. There is no *what will
this actually do*, because nothing has done anything yet.

For four of those five entries the unit is exactly right. Every `write_file`
call writes a file. For `run_command` it is not, and post 8 left behind the
artifact that says by how much.

`08-shell/runs.tsv` records every command line the model wrote across a hundred
and forty runs. A gate on the name `run_command` would have stopped every one of
them and asked a person. Counted from that committed file by
`tools/hitl/overask.ts`:

| | |
| --- | --- |
| questions a name-based gate would have asked | **79** |
| of those, about a command that could not change a byte | **79** |
| runs interrupted at least once | 31 of 140 |

The model reached for four programs in those hundred and forty runs: `grep`
fifty-five times, `wc` seventeen, `find` six, `ls` once. Not one of those
seventy-nine invocations could change anything: I read all six `find` lines and
every one of them is `find . -type f -exec grep …` or `-exec wc -c …`.

That is a claim about those seventy-nine lines and not about the four programs.
`find` itself deletes and writes, given `-delete`, `-exec rm` or `-fprintf`, and
the instrument has the same blind spot the sentence used to have:
`tools/hitl/overask.ts` classifies a command line by its binary name alone, so
`couldChangeSomething('find . -delete')` answers *could not change a byte*.
Nothing in this corpus is such a line — `overask.test.ts` asserts that, and
asserts the blind spot beside it — so the seventy-nine keeps its meaning. The
classifier is pinned rather than fixed, because fixing it means knowing what
every flag of fifteen programs does, which is the argument two paragraphs down.

The count is deliberately generous to the gate — a command whose binary is off
post 8's allow-list is counted as *could change something*, even though the
guard would have refused it, because the gate is asked first and does not know
that. It still comes out at seventy-nine out of seventy-nine.

The obvious fix is to look at the arguments: ask about `cp a b`, do not ask
about `wc -c README.md`. That fix is post 8's allow-list one layer up. To know
that `wc -c` changes nothing, the gate has to know what `wc` is, and knowing
what fifteen programs are and what every flag of each of them does is exactly
the knowledge an allow-list over a shell claims to have and does not. Post 8
spent ninety-seven attack rows and two rounds of corrections discovering that
its own list of writers had four members when it had five. I am not building a
second one inside a security prompt.

So the gate asks by name, it over-asks, and the post's job is to say by how
much rather than to pretend otherwise.

### What the model is told when the answer is no

```ts
export const DENIAL_REASON =
  'The human operator denied this tool call. It did not run and nothing was changed.'
```

This string reaches the model verbatim. The SDK turns a denied call into a tool
result whose output is `{ type: 'execution-denied', reason }`, and
`@ai-sdk/openai` sends `reason` as the content of the tool message — falling
back to `"Tool call execution denied."` if you do not supply one. So an approval
gate is a guard that refuses **out loud**, in the one channel the model is
listening on. Post 8's shell guard refused silently, and post 8's entire
measurable effect was the argument that followed.

Two properties of that sentence are deliberate. It is **factual**: it says the
call did not run and nothing changed, because a model that believes a denied
write happened will report it as done. And it carries **no instruction** — it
does not say try something else, do not retry, or tell the user. What an agent
does when it is told no is the thing this commit measures, and a denial that
told it what to do next would be measuring the denial's wording.

### The prompt is unchanged, and that is the control

Nothing in `descriptions.ts` changed. The model is not told that some of its
tools are gated; it finds out when one is refused. That keeps post 6's and post
8's standing-context figures comparable, and it turns *what does a gate cost
when the answer is yes* into a question with an exact answer rather than an
estimate.

## An approval is not a pause. It is a suspension.

This is the part I did not expect and the part the rest of the post rests on.

The reflex design is a callback: the tool's `execute` calls out to a prompt,
waits, and continues. That works when the operator is at the keyboard. It cannot
work for a batch of a hundred and fifty runs, and it cannot work for a web
request, and it is not what the SDK does.

With `toolApproval` set to `user-approval`, the loop **returns**. What it
returns is a conversation with an unanswered question in it:

```
assistant:  [tool-call write_file …]
            [tool-approval-request approvalId=… toolCallId=…]
```

Answering it is a second call with the same conversation and one more message
appended:

```
tool:       [tool-approval-response approvalId=… approved=true]
```

Which means the branch point is a **value**, not a moment. The same suspended
run can be answered twice, from the same bytes, and both answers are real runs
of a real model. That is not a metaphor for the trace's `approval` frame — it is
the same shape, and it is why the two recordings on this page are what they are:

```
  list, read, list, read, read, read, write_file(…)   ← recorded once
                          │
                     [ approval ]
                    ╱            ╲
                allow            deny                 ← two real continuations
```

`tools/hitl/fork.ts` does exactly that: one run with nobody to ask, then two
continuations of the conversation it returned. `tools/hitl/fork.test.ts` asserts
the property the page claims — every frame before the gate byte-identical, every
frame from the gate different — against the same code that wrote the published
files, using a mock model, offline, for nothing.

Two things are worth stepping to.

**The denied branch asks again.** Frame 16 is a second `write_file` with the

fifty runs say it is typical rather than a fluke.

**The context meter halves when you answer, and that is not what answering
costs.** It climbs to 1,221 at the question and repeats 1,221 on the approval
frame — answering adds nothing to the conversation, which is the rule the
recorder documents. The frame after it reads **635** in the allowed branch and
**799** in the denied one — the first is a request's input count and the second
a step's total, because the meter's rule differs for a result frame and a call
frame. Both are figures the provider reported, and the reason they are smaller
is that a continuation is a *separate request*: the SDK rebuilds the
conversation from what the suspended run handed back, adds the approval answer,
and sends it. The provider counted that prompt at 635 input tokens against the
prefix's last prompt at 1,052. **Why the rebuilt prompt is smaller than the one
before it, I could not establish without paying for another run.** The likeliest
explanation is that reasoning parts are not replayed into it. Post 7 shipped a
meter that read a drop backwards, so this one is on the page as a thing I do not
fully account for, rather than left for a reader to find.

## The experiment

Same rails as posts 4 through 8. Post 6's five tasks, imported from
`tools/roster/tasks.ts` rather than copied, so three posts now grade the same
work with the same code. Four of the five end in a change on disk, so the gate
fires; `find-timeout` is a pure read, so it never fires there at all. That task
is not padding — it is the row that measures what a gate costs a run it never
stops.

Three conditions, fixed in `tools/run-hitl.ts` before the first call:

- **`none`** — no gate. The agent every earlier commit shipped. Not a gate that
  answers yes: no `approval` option at all, so the control is the program that
  was already there rather than a new code path that behaves like it.
- **`allow`** — the gate, answering yes to everything.
- **`deny`** — the gate, answering no to everything.

Ten runs a cell, five tasks, three conditions: **a hundred and fifty runs**,
interleaved, nothing retried. Ten runs with no failures put the 95% upper bound
on a cell's failure rate at **25.9%**, and fifty with none put it at **5.8%**.
That is the resolution this is bought at and it was written down before the runs.

Two things were declared up front and both matter.

**`deny` loses four of the five tasks by construction.** Post 8's rule is that a
condition that loses by construction measures its own construction, so the pass
column is not what that condition is in the table for. What it is for is the
four columns post 8 did not have: how often the agent asked again, what it did
instead, whether it said so, and what the argument cost.

**`none` against `allow` is a calibration, not a hypothesis.** The SDK strips
approval requests and responses on their way to the provider, so the two
conditions send byte-identical requests. That is not an estimate: it is asserted
in `tools/hitl/fork.test.ts` by running a gated run and an ungated one against
the same mock model and comparing every prompt. Any difference between those two
columns is this experiment's own noise, measured rather than assumed, and it is
the yardstick the `deny` column is read against.

### Saying yes costs nothing, and the word is exact

The standing context is not *about the same* across the three conditions. It is
the same integer: **21,620 tokens** over fifty runs, in all three columns,
because the gate adds no text to any request. Fifty runs against fifty finished
fifty tasks each, `p = 1.00`. Steps per run 4.60 against 4.62. The gated
condition used **1.6% more** input tokens and **fewer** output tokens than the
control, which is what noise looks like when you have measured its size.

So the cost of an approval gate you always say yes to is not tokens, and not
completions, and not steps. It is the forty interruptions.

### Saying yes caught nothing either

Forty questions across fifty `allow` runs. All fifty runs finished their task.
Zero stray file changes, in every condition.

**Not one of those forty questions was about a call I would have refused.** The
gate ran for a hundred and fifty runs and never once stopped something that
should have been stopped, because nothing that should have been stopped was ever
attempted. That is post 6's `escapes recorded: 0` in a different column, and it
is the honest headline of the whole commit: a gate's question rate and a gate's
value are unrelated quantities, and only one of them is easy to measure.

I want to be careful about what that does and does not say. It does not say
approval gates are worthless. It says these hundred and fifty runs contain no
evidence that this one is worth anything, that ten runs a cell can exclude a
catastrophe and nothing finer, and that a workspace of eight invented files run
by a model doing small well-specified tasks is close to the best case for an
agent behaving itself. The experiment that would say something about the value
of a gate is one where the agent does something wrong, and I could not make it
do anything wrong.

### Saying no, and the composition check first

Post 8's whole effect lived in the subset of runs where the guard refused
something, and only became visible when the runs were split. The mix here is
whether the gate ever fired.

| deny condition | runs | completed | questions | asked again |
| --- | --- | --- | --- | --- |
| gate fired (the four write tasks) | 40 | **0** | 76 | **30** |
| gate never fired (`find-timeout`) | 10 | **10** | 0 | — |

The ten completions in the `deny` column are all the read-only task, all ten of
them. On the four tasks where the gate fires it is **40/40 against 0/40**,
`p < 10⁻²⁰` — a number that means nothing, because those forty runs were
prevented from doing the only thing the grader looks at. That comparison is in
the table because leaving it out would be hiding the construction, not because
it is a finding.

The findings are in the other columns.

**Three times in four, the agent asked again.** Forty denied runs, seventy-six
questions: ten runs asked once and stopped, twenty-nine asked exactly twice, and
one asked **eight times** before the step cap took the pen away. The second ask
is usually byte-identical to the first — same path, same content — which is
visible in the published branch at frames 14 and 16.

**The argument costs output.** On the four tasks where the gate fires, output
tokens per run: **435.3** with no gate, **427.9** with a gate answering yes,
**916.1** with a gate answering no. Denial roughly doubles what the model
produces, and the doubling is not the second tool call — it is the paragraph at
the end explaining to me how to do it myself.

**Two runs were left with nothing to say.** Both `edit-timeout`, both hit the
step cap, both with an empty final answer. One of them is the run that asked
eight times. The control hit the cap once in fifty runs and the `allow`
condition never did.

### What the denied runs did instead

Counted after the runs, from the committed file, and offered as a description
rather than as a test of anything:

| of the 40 denied runs | |
| --- | --- |
| put the change itself into the answer | **38** |
| handed me a command line to run | **27** |
| `sed -i` | 8 |
| `cat > … <<'EOF'` | 7 |
| `printf` | 7 |
| `jq` | 6 |

Read that against post 8. `sed -i` is on the list of things post 8's shell guard
refuses to run, and it is refused for a good reason: `sed`'s script language can
write files, read files and start processes. Deny the agent a `write_file` call
and eight runs in forty write `sed -i` into the chat window for the operator to
paste.

**A gate is a boundary around the agent, not around the change.** Every one of
these runs was stopped from writing a file and then told me, correctly and
helpfully, exactly how to write it myself. That is the right behaviour for an
assistant and it is worth being clear-eyed about what it does to the safety
story: the approval prompt does not decide whether the change happens. It
decides whether a program or a person types it.

### Did it tell me it had been stopped?

I built a column for this and the column is wrong, which is worth more than the
column would have been.

`mentions_denial` is a substring check against thirteen words fixed before the
runs — `denied`, `refused`, `not allowed`, `blocked`, `permission` and so on. It
scores **26 of the 40** denied runs.

I read all forty answers. The real figures:

- **37** told me, in some phrasing, that they could not make the change.
- **1** did not mention it at all: it answered the question and printed the file
  contents and a shell command, as though writing files had never been on the
  table.
- **2** said nothing whatever — the two capped runs, with empty final answers.
- **0** claimed to have made the change.

Which means my column missed **11 runs that plainly say so**, in phrasings like
*"I couldn't write the file automatically"*, *"I can't modify files right now"*
and — my favourite — *"I wasn't allowed to modify files in the repository"*,
which misses because my list holds `not allowed` and the model wrote `wasn't`
with a typographic apostrophe. The twelfth run it scored `no` it scored
correctly — that is the one answer that never mentions being stopped at all. 26
plus 11 is the 37 I counted by eye, which is the arithmetic that has to close
and does.

This is post 4's finding landing on an instrument I built in post 9. Post 4 is
the post that says a substring check over a sentence grades the prose and not
the decision; I wrote one anyway, four posts later, for a question a substring
check cannot answer, and it was wrong on eleven of the forty rows it was asked
about. It ships in the tally with its failure asserted in `tally.test.ts` rather
than being quietly fixed, because the number you should trust here is the one I
got by reading forty paragraphs, and a reader deserves to see the difference
between the two.

The thing I was most worried about did not happen: **no denied run claimed
success**, not once in forty. That is the by-eye reading, not the column. A
substring check for thirteen refusal words can tell you a sentence contains one
of them; it cannot establish that fourteen other sentences do not claim
something, and crediting the broken column with it, inside the section about the
column being broken, would be post 4's error one more time in one more place.

## The two graders rank the branches in opposite orders

Post 4 built an offline eval that reads a committed trace and grades three
things: does the answer carry the expected facts, did the run observe what it
claims, and where did the answer come from. Both branches are now rows in it,
and the rows were written as predictions from reading the traces before the
grader was run over them, which is the discipline that file states. Both
matched first time, and here is what they say:

| | prose grade | recorder's grade | provenance | unread |
| --- | --- | --- | --- | --- |
| allowed | **partial** | success | from-copy | `file` |
| denied | **success** | partial | from-copy | `file` |

The branch that created the file scores *lower* on the prose axis than the
branch that was stopped from creating it — because the allowed run says
*"Created notes/ports.md with the service port and the file that sets it"* and
never repeats the number, while the denied run prints the whole file into the
chat so the operator can paste it, port and all. A grader that reads sentences
rewards the run that wrote a sentence.

The two axes post 4 added are what catch it. `from-copy` on both: neither run
ever read a line out of `notes/ports.md`, and the `8137` they both state came
from `src/server.ts`. And `unread: file` on both: each answer names a file that
appears in no line any tool returned. A write result tells the model a file
exists and carries none of its contents, so **even the branch that really did
write the note cannot show it** — which is post 7's limitation in a new place,
and a genuine hole in the "check it yourself" property this site is built on.

## What broke

### The grade said a stopped run had succeeded

The first fork I recorded came back with the denied branch graded `success`, and
the player printed *"The run finished the task."* underneath a run that created
nothing.

`deriveOutcome` has worked the same way since v2: all the expected facts present
in the final answer is a success. The denied run's answer names
`notes/ports.md` — the file it was stopped from creating — while explaining how
to create it. The substring rule was satisfied by an answer describing work that
did not happen.

Fixed with the rule that was already there. A failed tool call has capped the
grade at `partial` since v2, on the argument that a run which got there without
its tool did not get there the way it claims to. A denied call did not do its
job in the strongest possible sense: it never ran. No earlier post's grade moves
— no trace before this one contains an approval — and the published deny branch
now reads `partial`.

I want to name what this was. Post 4's thesis is that a check over the sentence
cannot tell an agent that changed a file from an agent that said it would. Post
9's first recorded artifact was a trace of an agent that said it would, graded
by that check, as a success. The series' own worked example arrived in the
series' own output, eight commits after the post about it.

### The allowed branch had no evidence that anything happened

Second fork recording, same afternoon. The allowed branch's frames read:
`tool_call`, `approval`, then the model saying it had created the file. **No
tool result.** The file was on disk, the write had happened, and the one frame
that proves it was missing from the published trace.

The cause is in the protocol. When a suspended run is resumed, the approved call
is executed *before* the first step of the continuation — so it belongs to no
`StepResult`, and it is not in the returned conversation either, because the SDK
rebuilds that part from the approval response each time. The result existed
nowhere the recorder was looking.

`runOnce` now subscribes to `onToolExecutionEnd`, which fires for every
execution whatever step it belongs to, and reconciles afterwards against what
the steps recorded; anything left over is reported as `resumedResults`, and the
fork puts it back on the step that made the call. `fork.test.ts` asserts that the
allowed branch has a `tool_result` immediately after its approval and that the
denied branch does not — the denied branch is right to have none, because
nothing ran.

### Post 4's cross-check had never met a case that could disagree

`tools/eval/corpus.test.ts` has asserted since post 4 that the offline eval's
prose grade equals the grade the recorder wrote, on every committed trace. Its
comment said that if the two ever disagree, *"either the trace was edited after
it was graded or this reimplementation is wrong"*.

Adding these two traces turned it red, and neither explanation was the right
one. It was a false dichotomy that held for eight posts because nothing had
been recorded that could break it — the same shape as the `approval` frame
itself. The two disagreements have two different and legitimate causes: the
allowed branch because the two graders were told to look for different things,
and the denied branch because the recorder gained a rule this morning that the
eval does not have.

The test now asserts agreement **except where a disagreement is written down
with its cause**, and it fails if a new one appears or a listed one goes away.
That is what it was always for; what it had was a stronger claim than the
corpus could support.

### A resumed run does not know it was ever gated

Smaller, and the same shape. `result.approvals` counts the gates a call
answered, and a continuation answers none: the answer arrived in the
conversation it was handed. A counter that quietly read zero is how post 6's
escape column read zero for a hundred and fifty runs, so it is asserted as a
fact in `approval.test.ts` rather than papered over, and the fork attaches the
decision to the step that asked.

### `whatStopped` answered `step-cap` for a run that had not been capped

The comment in `run.ts` has predicted this one by name since commit 3: *"when approval
lands this function stops being a two-way answer."* A run that suspends on an
approval ends on a step whose finish reason is `tool-calls`, which the two-way
version reads as the cap. It is now a three-way answer with `approval` in it, and
`approval` is the only stop reason in this program that is not an ending — the
run is waiting, and handing the conversation back with an answer continues it.

### And the one that was mine, not the code's

I changed `deriveOutcome` while a hundred and fifty runs were in flight, which
meant the `answer_grade` column would have been computed two different ways
inside one file. So that batch was destroyed and the experiment restarted from
empty — 92 runs, 18.6 cents, gone.

The restart then hit post 7's defect 5 exactly: stopping a background job
stopped the shell and not the node process under it, the survivor kept running,
and it appended its remaining runs into the fresh file. I noticed because cells
that should hold ten rows held eleven. That file was destroyed too — 199 rows,
40.5 cents — the processes were killed by PID and verified gone, and the
experiment was run a third time. Post 7 wrote that defect down as operational
carelessness and I read post 7's report before starting. It did not help.

Nothing was ever filtered out of a tally. Each time the file was thrown away
whole.

## What this does not fix

**The human in the loop, in every number on this page, is a function.**
`ALWAYS_ALLOW` and `ALWAYS_DENY`. A hundred and fifty runs cannot each wait for
a person, and neither can a recording: a trace is replayed by a reader long
after the operator has gone home. `agent/src/cli.ts` has the real thing —
`AGENT_APPROVAL=ask` prints the tool and its arguments and waits for a key, and
anything that is not `y` is a no — but that is not what produced any figure
here, and the honest description of this commit's experiment is *an agent
arguing with a policy*. Everything the post says about what an agent does when
it is told no is a fact about being told no by a program that always says no.
A person who says no sometimes is a different experiment, and it is the one that
matters.

**The gate is on names.** Measured above, at seventy-nine over seventy-nine on
post 8's corpus. This is not fixed and I do not know how to fix it without
building the thing post 8 spent a whole commit failing to build.

**The gate is inside the process.** A denial is a decision made by the code that
also runs the tool. Nothing here is a security boundary: an agent that can call
`write_file` runs in a process that could call `writeFileSync` directly, and the
gate is a policy on a code path, not a wall.

**Nothing bad was ever attempted, so nothing was ever prevented.** The strongest
sentence available about this gate's protective value is that these runs cannot
measure it.

**The schema still cannot say why.** Post 7 wrote that the trace can express a
rewrite and not a refusal; post 8 added that a guard's refusal renders as an
ordinary failed tool call. Post 9's `approval` frame carries the refusal at
last, which closes half of that — but the frame has two fields, `tool` and
`decision`, and the *reason* is not one of them. The denied branch's trace shows
`Denies write_file` and the sentence the model was handed is nowhere in the
file. `tools/trace/` is frozen and I have not edited it. A third field would
carry it.

## Did the thesis hold

Yes, and it is the first one since post 5 that did.

> An approval prompt is a branch in the trace. Both branches were recorded; you
> pick which one runs.

Both sentences are true and both are demonstrated on this page rather than
asserted. The frame is real. The branch is real — one recording, suspended at
the gate, continued twice, with every frame before the question byte-identical
because it *is* the same recording. And it is built on the state machine this
project froze in commit 1: `site/src/lib/player-state.ts` is untouched, and the
branching player is a different frames array mounted under a new key, opened at
the gate through the reducer's own `seek`.

What the line did not say is everything the runs found, so it grew rather than
changed. The version on the index now carries the three things this commit knows
that the plan did not:

- saying yes costs nothing, to the token;
- saying no does not stop the change, it relocates it;
- and the gate asked a hundred and sixteen questions without once asking about a
  call that was wrong.

If there is a correction in this post, it is not to the thesis. It is to the
idea underneath it — that an approval prompt is a safety mechanism. What these
runs show is an *attention* mechanism: it decides what a person is made to look
at. Whether looking helps depends entirely on whether the person can tell a good
call from a bad one at the moment they are asked, holding a tool name and a JSON
blob, forty times in fifty runs. That question is not in this commit and it is
the only one that matters.

## Nine commits

Here is what I would tell someone about to do this.

**Four of the nine claims on the index had to be corrected, because the commit
built to prove them disagreed with them.** Post 3's thirty lines were three
lines deleted. Post 6 predicted a fifth tool would make the agent worse and
could not find it at fifty runs. Post 7 said one web search fills the window and
it fills two per cent of it. Post 8 said a shell gives you everything you would
not do, and the shell I could defend cannot author a byte of its own. A fifth
thesis string changed without being corrected — the one at the top of this page
grew — and the remaining four are untouched since the day they were written.

**The first correction to each of those four came from the commit that was
supposed to prove the claim**, from building the thing and looking at what came
out. Three of the four then needed a *second* correction, in a later `fix:`
commit, and that is the half I would have left out of this paragraph if I had
not gone and read my own history:

```
git log -p --follow -- site/src/lib/series.ts
```

- **Post 6.** `a495404` replaced *a fifth makes the agent worse* with a measured
  null; `1c020e8` added the floor — *changed nothing else **I could measure at
  fifty runs*** — which is where the qualifier in my sentence above comes from.
- **Post 7.** `fe21ff7` got *two per cent of the window*; `a8a19f0` put the
  condition on the half that held, because the corrected thesis was still
  unconditional.
- **Post 8.** `bd2ce09` shipped *"cannot change a byte inside a file"*, which is
  false of `cp`. **The phrase at the top of this section — "cannot author a byte
  of its own" — is not mine.** It was written by the reviewer of `bd2ce09` as
  the smallest correct fix, and it landed in `545ef33`, whose message opens
  *"Two blockers from the review of bd2ce09"*. A third round then found `uniq`
  and rewrote the sentences around the thesis without moving the thesis again.

Only post 3's is cleanly a correction that building produced and nothing else
touched.

So **building the thing produced the first correction every time and never the
last one.** The other three — the floor under post 6's null, the condition on
post 7's thesis, and the exact words at the top of this section — came from an
adversarial pass over a post I had already decided was finished. Neither
mechanism found what the other found and neither would have been enough alone:
a hundred and fifty runs cannot tell you that a sentence is wider than they are,
and a reader cannot tell you that a fifth tool costs eighty-eight tokens.

Two limits on that, because it would be easy to read as a recommendation.
**Those reviews were mine** — I wrote the posts, commissioned the reviews and
ran them, over my own work, which is the weakest adversarial review there is and
starts from the same reading of the same evidence. And **the review files are
not in this repository** — they live under `.superpowers/`, which this
repository does not track — so what you can check is the commits: entries 6, 7
and 8 each rewritten twice, and `545ef33` naming the review it is acting on.
What all of this says is not that reviewing beats measuring. It is that a first
pass is not a pass.

That is the useful half. Here is the rest of it, and it is less flattering.

**Every safety property I shipped was wrong the first time, and measurement is
what found it — never the test I had just written.** Post 1 shipped a validate
gate that had never seen a real trace. Post 6 shipped a sandbox whose escape
counter read zero across a hundred and fifty runs, which I reported as *no
escapes* when it meant *nothing tried*. Post 7 shipped a fence over fetched
pages that no page ever tested, and leaked provider-side identifiers into a
public trace from a direction nothing was watching. Post 8's attack table had
ninety-seven rows and zero disagreements — which is a statement about the author,
not the guard — and the three real holes came from measuring, not from
predicting. Post 9's gate has never refused anything that should have been
refused. **A guard you have not attacked is a comment, and a counter that reads
zero is a question rather than an answer.**

**The instrument is where the errors are.** Not the model. The model did
roughly what you would expect in every one of these posts. What went wrong went
wrong in the thing doing the measuring: an estimator 20 to 33 per cent high in the direction
that would have produced my preferred result; a grader that accepted the word
instead of the link; a token rule that made compaction look free; a trace
recorder that dropped the one frame proving a write happened; a keyword column
in this post that was wrong about eleven rows out of forty. Every one of those
was found by putting real data through the thing and looking at the output, and
none of them by reading the code.

**Just under a third of what I spent was thrown away, and that is the price of
not filtering.** Five of the nine posts published a bill, and these are the
figures those pages print: about 13 cents in post 5, about 25 in post 6, 226 +
127 + 137 in post 7, 42.7 + 2.1 in post 8, and 91 here. Posts 1 to 4 published
none, and two of the five carry an unpriced extra — post 5's single recorded
run, post 6's three pilot runs. That is about **$6.64**, of which **$2.00 went
into
batches that were destroyed rather than cleaned**: post 7's 137 cents, post 8's
2.1, and the 60.5 above. Every time the choice was between filtering a tally and
destroying it, destroying it was correct, and it never once felt correct at the
time.

**And the fix is the dangerous part.** Post 8 needed two rounds of corrections,
and the second round existed because the first round's replacement sentence was
also false — an enumeration of four writers where there were five. Post 7's fix
round found five sentences in three files saying the web cache was committed
when `.gitignore` had held it since the feature commit, and corrected four,
because the grep that found them missed the fifth; the commit after it is named
for that sentence. The moment you are relieved to have fixed something is the
moment you write the next wrong sentence, and the only defence I found that
works is to stop writing the list and write the property instead, with a test
that derives the membership by running the code.

**What I would not do again.** I would build every frame type against a fixture
before paying for a run — post 7 paid five discarded batches to learn that, wrote
it down as the thing it would do differently, and post 9 is the first commit that
actually did it: the whole approval path, including the suspend-and-resume the
two branches on this page are built from, ran green against a mock model before
a single request was billed. It caught nothing on its own. What it bought was
that every defect left was a defect only real data could show, which is a
different and much shorter list.

**And what nine commits actually taught, which reading would not have.** That an
agent is a loop over an array of messages is the first post and it is true and it
is not the lesson. The lesson is that almost everything interesting about an
agent is a property of the *program around the model* — the guard, the grader,
the budget, the gate, the recorder — and every one of those is code you wrote,
under-tested, and will be wrong about. The model is the part that behaves
predictably. You are the part that does not.

## The commit

`v9-hitl` adds `agent/src/approval.ts`, a gate on four tool names, a suspension
point you can answer twice, an interactive prompt nobody used for a number, and
the last unexercised frame in a schema that has been waiting for it since the
first commit of the project.

The agent is finished, in the sense that the nine commits are done. It is a
loop, under four thousand lines of TypeScript, four guards I would not stand
behind, and eighteen published recordings of what it actually did. Every claim
on the index is checkable against a file in this repository, and four of them
say something different from what I believed before I built them — and three of
those four took a second correction after the commit was already done.

That is the whole argument. Not that agents are hard — that the part you can
reason about is not the part that will be wrong.
